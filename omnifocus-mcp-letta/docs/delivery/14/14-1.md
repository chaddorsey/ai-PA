## Requirements
- Draft input/output schemas for `markTaskCompleted`, `listUncompletedTasks`, `listProjects`, and `moveTaskToProject`.
- Identify shared serialization helpers to reuse (tasks/projects metadata).
- Document error handling conventions (e.g., JSON-RPC errors vs success payloads).
- Decide on availability check mechanism for `onlyAvailable` filter.
// Schema/Handler Design Notes
- `markTaskCompleted`
  - Input schema: `{ taskId: string }` (required).
  - Output payload (success): `{ taskId: string; completionStatus: "completed"; completedAt?: string }`.
  - Errors: missing `taskId` (JSON-RPC `INVALID_PARAMS`), unknown task (JSON-RPC `NOT_FOUND`), already completed should still return success with idempotent response (optional `alreadyCompleted` flag) or treat as success and include note.
  - Handler should call existing bridge command `completeTask` and reuse task serializer if including metadata; for minimal output, create small response object.
- `listUncompletedTasks`
  - Input schema: optional filters `{ projectId?: string; onlyFlagged?: boolean; onlyAvailable?: boolean }` with defaults `false`.
  - Output array of task summary objects: `{ taskId, name, projectId, inInbox, flagged, created, due, deferred }` with each field optional except `taskId`/`name`.
  - Implementation relies on existing `listRemaining` / `queryTasks` command; apply filters client-side if backend lacks direct support. `onlyAvailable` should use OmniFocus availability logic (e.g., check `task.isAvailable` or derived state from bridge data). Reuse existing serializer or derive from consolidated task output via helper `pickTaskSummaryFields(task)`.
- `listProjects`
  - Input schema includes options `{ folderId?: string; listProjectNames?: boolean; listByFolder?: boolean }`. When `folderId` provided, filter results; `listByFolder` returns grouped structure.
  - Output when not grouped: array of `{ projectId, name, description?, taskIds: string[], tasks?: Array<{ taskId, name }>, folderId? }`. If `listByFolder` true, output `Array<{ folderId: string | null; folderName: string | null; projects: ProjectSummary[] }>`.
  - Handler should reuse project serializer and optionally attach task names by mapping over `project.tasks` with shared helper from consolidated operations.
- `moveTaskToProject`
  - Input schema: `{ taskId: string; projectId: string }` (both required).
  - Output payload: `{ taskId, projectId, status: "moved" }`.
  - Errors: missing ids (`INVALID_PARAMS`), nonexistent entities (`NOT_FOUND`), move failure (`INTERNAL_ERROR` with message). Handler should call existing move command ensuring sequential project constraints handled upstream.
- Shared considerations
  - Add new schema definitions to `schemas.ts` (Zod objects) for reuse by server handlers and potential tests.
  - Ensure all new tool schemas reference `detailLevelEnum`/`sortOrderEnum` only when needed (likely not required for quick tools to keep them minimal).
  - Document handler mapping in `server-mcp-simplified.ts` (tool registration, command translation, response shaping).

## Implementation Plan

- Record notes on error response structure to guide implementation tasks.
- Define helper functions `buildTaskSummary`, `buildProjectSummary` referencing consolidated serializer outputs.
- Plan to centralize error mapping (e.g., `mapBridgeErrorToJSONRPC` helper) to ensure consistency across new tools.
- Update documentation of tool registry to include quick-access tool metadata once implemented.
