# #3205 Wire Capture Results — Definitive

## Method

Built a one-line-instrumented Letta image (`letta-local:0.16.7-dbg3205`) that adds `logger.info("[DBG-3205] approval payload: %s", input_message.model_dump_json())` at the top of `create_approval_response_message_from_input` in `/app/letta/server/rest_api/utils.py`. Switched the live container to it, ran the failing Task workload via letta-code, captured all approval payloads on the wire, then reverted to stock image.

Total downtime: ~75 seconds for image swap + readiness, no data lost. All pilot agents created during the test were deleted afterward.

## Definitive Findings

**1. The wire format is exactly correct.**
- `approvals` array contains properly-shaped `{type:"tool", tool_call_id, tool_return, status, stdout, stderr}` entries
- The deprecated top-level fields (`approve`, `approval_request_id`, `reason`) are all `null` — letta-code never uses them
- The `tool_call_id` values are real OpenAI-style call IDs (`call_*`), never `message-*` prefixed
- The migration validator at `ApprovalCreate.migrate_deprecated_fields` was never going to fire (because `approve` and `approval_request_id` are null) and didn't need to

**2. The server's approval-state tracking is fine.**
- `approval payload: ...` log lines appear immediately on each approval submission
- The server correctly receives and parses each approval response
- `final_stop_reason=requires_approval` runs are forced [DONE] after their tool_return is processed — that's normal completion, not a stuck state
- The "Cannot process approval response: No tool call is currently awaiting approval" error from #3205's filer never appeared in our logs

**3. The actual failure is on the LETTA-CODE CLIENT SIDE, in the Task subagent launcher.**

The `tool_return` content tells the whole story. Each entry contains an error message generated by letta-code BEFORE any data left the parent process:
- `"Error: Invalid system prompt \"explore\""` — the *child* subagent process rejecting `--system explore` because `explore` isn't in the validator's allowed list
- `"Error: Invalid subagent type \"default\""` — the *parent's* Task tool validator rejecting `default` as not in the BUILTIN_SOURCES list
- `"Failed to parse subagent output: Unexpected end of JSON input"` — the parent's stdout parser failing because the subagent process exited without producing valid stream-json

The retry pattern is the LLM observing failure and trying alternatives — sane behavior given garbage subagent results.

## Root Cause: `letta --new-agent -p` Headless Mode Fails Silently

Direct reproduction confirmed the bug shape:

```bash
# Works perfectly:
letta --agent <existing-id> -p "say OK"
→ stdout: "OK", exit 0, ~3-4s

# Silently fails:
letta --new-agent --no-memfs -p "say OK"
→ stdout: empty, stderr: empty, exit 0, ~6s
   No new agent created on the server
   No network connection to localhost:8283 ever made
```

The failure persists across:
- Fresh `HOME` (no settings), with and without `LETTA_API_KEY` set
- All telemetry/auto-update env vars disabled (`LETTA_DISABLE_UPDATE`, `LETTA_OFFLINE`, etc.)
- `LETTA_CODE_AGENT_ROLE=subagent` env set (which `validateSystemPromptPreset` requires for `allowSubagentNames`)
- With or without `--system <subagent-type>`
- letta-code 0.23.8 AND letta-code 0.24.2 (auto-upgrade happened mid-test)

The subagent process loads dynamic libraries for ~3 seconds, then exits at ~6 seconds without producing any output, without contacting the configured Letta server. This is the underlying defect.

## Why This Was Mistaken For #3205

Both bugs produce the same surface symptom — Task tool calls produce empty results, LLM retries, agent appears stuck. The forum thread's diagnosis correctly identified the symptom but misattributed the cause to server-side approval state corruption (which IS a real bug per #3205's filer's repro, but not what's happening to us).

The misattribution is reinforced by:
- `final_stop_reason=requires_approval` runs in our messages table — this is **normal** behavior for client_tools, not a sign of corruption
- `Stream Finalizer Appending forced [DONE]` warnings — these fire on any `requires_approval` run that completes via approval response, not just stuck ones
- 5× LLM self-retries — the LLM sees error tool_returns and tries different `subagent_type` values, looking like a stuck loop

We carried the misattribution forward in our prior diagnosis (`./2026-04-24-letta-issue-3205-diagnosis.md`) and it propagated into the migration plan's Phase -1 framing. Both need correction.

## Secondary Findings

**`buildSubagentArgs` always uses `--new-agent` for fresh subagents.**
At line 72566 of letta-code's letta.js:
```js
} else {
  args.push("--new-agent", "--system", type);
  args.push("--tags", `type:${type}`);
  args.push("--no-memfs");
  if (model) { args.push("--model", model); }
}
```
This is the only path for fresh-spawn subagents. The `isDeployingExisting` branch only fires when `Task(agent_id=..., conversation_id=...)` is explicitly passed. So **every fresh subagent invocation hits the broken `--new-agent` headless path.**

**Base tools were missing from our self-hosted Letta.**
Pre-test: only `memory_apply_patch` and `memory` registered. `web_search`, `fetch_webpage`, `run_code`, `semantic_search_files` were absent. `POST /v1/tools/add-base-tools` (no auth required) successfully populated them. This was a separate prerequisite issue — without base tools registered, letta-code can't create new agents that include them. **Fixed during this test session.** Adding it to the migration plan as a one-time setup step.

**`explore` subagent type inconsistency.**
The OUTER Task validator in 0.23.8 lists `explore` as available, but `BUILTIN_SOURCES` in the SAME version contains only 7 entries (no `explore_default`). When the LLM passes `subagent_type=explore`, the outer accepts it, the launcher passes `--system explore`, and the spawned subagent rejects it because `explore` isn't in the loaded subagent configs. This is an upstream letta-code bug independent of `--new-agent` headless failure.

**The `validateSystemPromptPreset` allows-subagent-names gate.**
At line 167216:
```js
const allowSubagentNames = process.env.LETTA_CODE_AGENT_ROLE === "subagent";
```
If `LETTA_CODE_AGENT_ROLE` is not set on the spawned subagent's env, the validator only accepts the 5 static system prompts (`default, letta, source-claude, source-codex, source-gemini`) and rejects subagent type names. `composeSubagentChildEnv` correctly sets this env var on spawn — verified at line 72528. So this gate is correctly handled when subagents are spawned by letta-code. But if you run `letta --new-agent --system general-purpose` manually without `LETTA_CODE_AGENT_ROLE=subagent`, you get the truncated validator's error.

## What This Means for the Migration Plan

The current Phase -1 in `docs/plans/2026-04-24-001-feat-letta-memfs-upgrade-plan.md` is **misframed**. It's still oriented around patching the Letta server's approval state handling, which is fine. The actual blocker is upstream in letta-code, not in our self-hosted Letta server.

Three viable paths forward, in order of preference:

### Path R — Resolve `--new-agent` headless silent failure (in priority order)

This is the clean fix. The bug we identified is reproducible, narrow, and likely fixable. Investigation paths:
1. **Strace/dtruss the failing process** to find where it exits silently (requires root on macOS)
2. **Read `letta.js` for the headless mode entry path** — find what determines the 6s timeout and why it returns no output
3. **File an upstream issue against `letta-ai/letta-code`** with our reproduction. This is a different repo than `letta-ai/letta`, and the bug is small and specific. A maintainer with the source could fix it in minutes.
4. **Patch letta-code locally** to make `--new-agent -p` actually work, applied alongside the memfs client patch

### Path B — Bypass `--new-agent` in subagent spawning (workaround)

Patch `buildSubagentArgs` in letta-code's letta.js so that subagents are launched against pre-created agents instead of using `--new-agent`. The patch:
1. In `executeSubagent`, before spawning the child process, call the Letta REST API to create the agent
2. Pass `--agent <new-id> --new` to the subagent instead of `--new-agent`

This is a ~30-line letta-code patch. It avoids the `--new-agent` bug entirely and is testable independently. The downside: we maintain a fork of letta-code that drifts from upstream over time.

### Path A — Accept Task remains disabled and ship Path A memfs scope

Still viable. memfs upgrade work proceeds without Task. Consolidator patterns from the sibling brainstorm get deferred. Less aggressive but unblocks the immediate goal.

## Open Questions

- Why does `letta --new-agent -p` silently exit on our system? We did not pin this down. It happens consistently in 6 seconds, before any network call, regardless of env vars, settings file, or version.
- Does `letta --new-agent -p` work on Letta Cloud? If yes, the bug is self-hosted-specific. If no, it's a general headless-mode bug.
- Is the same bug present in lettabot's letta-code subprocess invocation? lettabot uses `--agent <existing>`, so it doesn't hit `--new-agent`. But subagents launched FROM lettabot's letta-code subprocess WOULD use `--new-agent` and would hit this bug.
