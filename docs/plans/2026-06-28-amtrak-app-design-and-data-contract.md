# Amtrak Route Guide → App — Design & Data‑Contract Spec

**Date:** 2026‑06‑28 · **Status:** spec for app planning (substrate complete) · **Package:** `tools/amtrak-position-engine/`

**Purpose.** This is the bridge document. The engine, the route‑guide data layers, and the full six‑leg narration are built and committed. This spec (a) describes everything the app will build on so a *fresh* context can pick up without the prior conversation, (b) proposes the app design, and (c) pins the **data contract** the client consumes. Read this, then plan the app.

---

## 1. What we've built (the substrate the app rests on)

A trip across six Amtrak long‑distance trains (the July‑2026 itinerary), each a "leg" keyed by its timetable id:

| Leg key | Train | ~Miles |
|---|---|---|
| `3` | Southwest Chief (Chicago–LA) | 2,265 |
| `2` | Sunset Limited (LA–New Orleans) | 1,995 |
| `58` | City of New Orleans (NO–Chicago) | 934 |
| `27` | Empire Builder (Chicago–Seattle) | 2,256 |
| `11` | Coast Starlight (Seattle–LA) | 1,193 |
| `422` | Texas Eagle (LA–Chicago) | 2,727 |

Everything is keyed to one axis: the leg's **anchor‑relative milepost**, with a bidirectional `milepost ↔ lat/lon` projection onto the on‑track GTFS polyline. That single contract is why position, ETAs, scenery, and narration all compose.

### 1.1 The position engine — `position_engine.py`
Stdlib‑only runtime (Python 3.9+, no third‑party deps, offline‑capable). Loads a committed `data/` bundle. Capabilities:
- **Predicted position:** `query_position(date, time_ET, …)` → most‑likely milepost + lat/lon + P10–P90 uncertainty window, from ~350 historical runs/route anchored to the published timetable. Validated to ~0.66 SD.
- **Conditioned forecasting:** given a real delay at a passed station (`--at STATION --delay MIN`, or auto from the live feed), reweights the historical ensemble (Gaussian kernel) → ~35% MAE reduction.
- **Live position:** `now` resolves **live → cached‑fix → predictor** (Amtraker feed `live.py`), degrading gracefully offline.
- **Projection helpers:** `_milepost_latlon(poly, mile) → (lat,lon)` and `project_to_leg(poly, lat, lon) → (mile, offtrack_mi, side)`. The latter is how live GPS becomes a milepost.
- **ETAs:** `eta_to` / `eta_to_mile` → conditioned P10/P50/P90 arrival times to any station or milepost.
- **CLI commands (also the function surface):** `now`, a timestamp, `eta`, `around`, `lookahead`, `alerts`, `profile`, `story`, `guide`, `test`.

### 1.2 The route‑guide data layers (`data/*.json`, committed, stdlib‑read)
Built once at "build time" (network + GIS), read at runtime as plain JSON. Each feature is projected onto the milepost axis with a left/right **side**.
- **`route_guide.json`** — per leg: `leg_miles`, `features[]` (stations, towns/cities, county **`area`** spans with `stats` = demographics/occupations/income/education + NASS top crops + NLCD land‑cover mix, scenic/natural/engineering features, auto‑detected summits/passes), a continuous **`elevation_ft`** profile, and a continuous **`landcover`** profile.
- **`route_lore.json`** — per leg: `lore[]` (≈1,293 points of interest — Wikipedia‑sourced towns/landforms/ghost towns/historic sites + GNIS gap‑fill named landforms; each with `peak_mi`, `lat`, `lon`, `side`, `offtrack_mi`, `summary`, `url`) and `counties{}` (per‑county Wikipedia summaries).
- **`route_science.json`** — per leg, four continuous milepost‑sampled profiles: `geology` (Macrostrat: formation/age‑Ma/lithology/description), `ecoregion` (EPA L1–L4), `fossils` (Paleobiology DB taxa+age), `hydrology` (USGS watershed + HUC2 region → Continental Divide crossings).
- **`route_connections.json`** — per leg: `categories[]` (recurring Wikipedia‑category threads) and `nodes{}` (per‑POI categories + Wikidata `named_after`/`part_of` + multi‑source `dates[]`).
- **`route_themes.json`** — per leg (L4): `overture`, 3–5 `theses` (name + thesis + `anchored_in` + `strongest_mi`), and 2–4 `movements` (inflection mileposts for step‑back essays).

### 1.3 The narration — `data/route_narration.json` (the primary app feed)
**2,900 units across the six legs** (per leg: 3→572, 2→502, 58→244, 27→560, 11→292, 422→730). Each leg is a milepost‑ordered list of two unit kinds:
- **squib** — a short (~60–130‑word) self‑contained mini‑commentary pinned to a specific POI milepost, window‑cued.
- **interstitial** — the connective fill between squibs: most often a *real, specific story* (historical or a scientific/natural deep‑dive) tied to the leg's theses; the look‑ahead/look‑back arc lives here too.

The narration was generated by **Claude Sonnet** in a fellow‑traveler **"we"** voice at ~**60% talking / 40% silence**, layering: L1 facts → L2 science + the dual‑granularity (near story ↔ macro arc) → L3 connections (cross‑layer chains, contemporaneity via a national `timeline.yml`) → L4 per‑leg theses, with a **spaced concept‑ledger** so big recurring ideas (the Western Interior Seaway, ghost towns, the railroad) are introduced once then re‑grounded occasionally through a fresh facet — never re‑defined. Every unit is **coordinate‑anchored** and carries **salience** + **theme** metadata (see §3.1).

### 1.4 The generation pipeline (for regeneration / extending / re‑voicing)
Repeatable per leg, all in `tools/amtrak-position-engine/`:
`themes.py` (L4 spine from a compact metadata fingerprint) → `build_leg.py <leg> <seg_mi>` (precomputes every ~60‑mi segment packet: macro arc + facts + L3 connections + timing budget + spine + the data‑derived concept‑ledger) → a **Workflow** fan‑out (one Sonnet subagent per segment, bounded concurrency, resumable) → `eval_leg.py` (scorecard: coverage / fill / repetition cadence / voice / theme balance / lint) → `normalize.py` (strip stray forbidden words, canonicalize theme tags) → `parse_narration.py` (→ `route_narration.json` with coordinates). The narrator contract lives in `narrate.py`'s `SYSTEM` + `macro_context`/`assemble`/`connect_context`/`timing_note`/`concepts_in_segment`/`memory_brief`.

### 1.5 Renderers already proving the "renderer over the contract" model
`kml_tour.py` (Google‑Earth fly‑ahead: polyline + placemarks + a timed `gx:Tour` with predicted clock times and modeled sun position per stop) — demonstrates that a front‑end is just a consumer of the milepost contract. The app is the next, richer renderer.

## 2. The app — what we're building

### 2.1 Concept
A **position‑aware audio rail‑travel guide**: a knowledgeable companion (geologist / ecologist / historian / observer of how people live) riding in the seat with you, narrating the country as it unfolds — granular stories overlaid on the leg's large gradients and connective themes — that you can also interrogate on demand. It runs **on the train, where signal is intermittent**, so offline‑first is a hard requirement.

### 2.2 Core experience — the always‑on track
- The app knows position (live GPS → milepost, or the predictor offline) and **plays squibs as we reach their mileposts**, filling the gaps with interstitial stories, targeting ~**60% talking / 40% silence** (silence is part of the design).
- **Fill is user‑tunable**: a slider from sparse (highlights only) to dense, implemented by selecting units by `salience` until the time budget for the stretch (distance × speed × TTS rate × fill%) is met.
- **TTS** turns unit `text` into audio; reading rate is user‑variable (and feeds the fill math).

### 2.3 Interaction modes (all read the same artifact)
| Mode | Anchored to | Behavior |
|---|---|---|
| **(always‑on track)** | position | play squibs at their mileposts + interstitials between, at the chosen fill |
| **What's that?** | current position | identify the most plausibly‑visible feature now — rank nearby squibs by proximity × `side` × prominence (`offtrack_mi`, `salience`, kind); answer from the squib (offline) or elaborate live |
| **Say More ▸** | a topic | deepen on a chosen dimension; the unit's `theme` + the POI's `route_connections` bundle seed a menu |
| **Why is that?** | a story/POI | reveal the connective web beneath it — the L3 edges (causal / thematic / temporal), from `route_connections` + `timeline.yml` |
| **Highlight mode** | — | play only high‑`salience` units |
| **Theme filter** | — | follow one of the leg's `theses` via the `theme` tag |

### 2.4 Online / offline split
- **Offline (default on the train):** the always‑on track, What's that?, and a set of **pre‑generated** Say‑More / Why cards all ship in the bundle and need no network. Position from the predictor (or live GPS hardware, which works without cell signal).
- **Live (when connected, or a small on‑device model):** arbitrary Say‑More / Why follow‑ups generated on demand, grounded in the stored `route_connections` bundle + `timeline.yml`. Offline this is a quantized local model; online it can use the hub LiteLLM.

### 2.5 Architecture sketch
```
 ┌─ Client (iOS / web) ───────────────────────────────────────┐
 │  Position service  ── live GPS → milepost (engine projection)│
 │                       │  or predictor (offline)              │
 │  Playback engine   ── selects units by position + fill +     │
 │                       salience/theme → TTS audio queue       │
 │  Interaction UI    ── What's that? / Say More / Why /        │
 │                       highlight / theme / fill controls      │
 │  Bundle (read‑only): route_narration.json + route_guide/lore/│
 │                       science/connections/themes + leg_shapes│
 └──────────────┬──────────────────────────────┬───────────────┘
                │ (offline: bundled)            │ (online/local‑LLM)
        position_engine (projection,     live Say‑More/Why generation
        ETAs, predictor) — port or              grounded in the bundle
        reimplement the milepost math
```
The engine is currently Python; the client either calls it as a service or **re‑implements the milepost↔lat/lon projection** (it's small) from `leg_shapes.json`.

## 3. The data contract (the interface the app consumes)

### 3.1 `route_narration.json` — primary feed
`{ "<legKey>": [ unit, … ], … }`, each leg milepost‑ordered. Unit shape:
```jsonc
// squib (pinned point)
{ "kind": "squib",
  "mile": 36,                       // trigger milepost
  "place": "Aurora, Illinois",
  "side": "ahead",                  // left | right | both | ahead
  "salience": 3,                    // 1–5 (5 = unmissable) → highlight + fill
  "theme": "The Persistent Corridor", // a leg thesis handle, or null
  "text": "Aurora — 180,000 people …",
  "lat": 41.76805, "lon": -88.28992,   // ON-TRACK trigger position (where the train is)
  "poi_lat": 41.76389, "poi_lon": -88.29, "offtrack_mi": 0.28 } // the FEATURE itself (squibs at named POIs)

// interstitial (connective fill over a span)
{ "kind": "interstitial",
  "from_mi": 28, "to_mi": 36,
  "salience": 3, "theme": "The Persistent Corridor",
  "text": "The geology is about to shift under us …",
  "lat": 41.77793, "lon": -88.2144 }   // on-track position at the span midpoint
```
All 2,900 units have `lat`/`lon`; the 1,293 named‑feature squibs also have `poi_lat`/`poi_lon`/`offtrack_mi`. Read‑time per unit ≈ `len(text.split()) / TTS_wpm`.

### 3.2 Supporting artifacts (for the interactive modes / map / stats)
`route_guide.json` (geometry, stations, county `stats`, elevation, land cover), `route_lore.json` (POI summaries + URLs + county notes), `route_science.json` (geology/ecoregion/fossils/hydrology profiles), `route_connections.json` (per‑POI categories/relations/dates — the **Say‑More / Why grounding**), `route_themes.json` (the spines), `leg_shapes.json` (the polylines for projection + map rendering). Schemas in §1.2 and the build doc `docs/plans/2026-06-26-amtrak-route-guide-build.md`.

### 3.3 The engine API the app needs
- `milepost → lat/lon` and `lat/lon → (milepost, offtrack, side)` from `leg_shapes.json` (port the two small functions, or call the engine).
- Predicted position for a clock time (offline, no GPS) + the live feed when online.
- ETAs to upcoming mileposts (for "coming up in ~N min" cues).

### 3.4 Trigger / playback model
1. Get position → current milepost on the active leg.
2. **Squibs:** fire the squib whose `mile` we've just reached (small lookahead so TTS starts a touch early).
3. **Interstitials:** between squibs, schedule interstitials whose `[from_mi,to_mi]` we're inside, chosen so total talk ≈ fill% of the available time; skip lower‑`salience` units when fill is low.
4. **Highlight / theme:** filter the candidate set by `salience` threshold and/or `theme` before scheduling.
5. **Re‑entry:** when a listener returns after a gap, prefer an interstitial (they carry the throughline) plus a brief theme‑anchored "where we are in the larger story" from `route_themes` + recent theme‑tagged units.

### 3.5 Say‑More / Why generation contract (live or pre‑gen)
Input: the anchor unit + its POI's `route_connections` node (categories, `named_after`/`part_of`, `dates`) + the leg `theses` + relevant `timeline.yml` events. Output: a short deepening (Say More = more on a chosen dimension; Why = the causal/thematic/temporal web). Pre‑generate the top‑N expansions per high‑salience POI for offline; generate the rest live (local model offline / hub online). Same grounding either way → no hallucination.

## 4. Open decisions to settle in app planning
1. **Platform** — native iOS (best offline + GPS + on‑device TTS/LLM; matches the earlier iPhone/AR aim) vs. a PWA. Likely iOS first.
2. **TTS** — on‑device (offline, free, decent) vs. cloud (better voices, needs signal); voice selection; reading‑rate control (feeds fill math).
3. **On‑device LLM** for offline Say‑More/Why — which quantized model fits (and how much we pre‑generate to lean on it less). The build‑time author is Sonnet; the *runtime* model is a separate, smaller pick (its own mini‑audition).
4. **Offline bundle** — `route_narration.json` (~2.8 MB) + supporting layers + audio. Decide: ship text + synthesize TTS on device, or pre‑render audio (bigger, instant). Per‑leg download.
5. **UI controls** — fill slider, highlight toggle, theme filter, the three on‑demand buttons, a map view (polyline + position + nearby POIs from `leg_shapes` + `route_lore`).
6. **Trip / train selection + multi‑leg** — pick the active train; handle the day‑by‑day itinerary.
7. **Position when GPS is weak** — blend GPS with the predictor; the engine already does live→cached→predicted.
8. **Audio caching / pre‑fetch** ahead of position.

## 5. Suggested phasing
- **P1 — Read‑only player:** load the bundle, position via GPS→milepost (or a manual/sim position), play the always‑on track with on‑device TTS + the fill slider + highlight/theme filters. Proves the contract end‑to‑end.
- **P2 — On‑demand modes:** What's that? (offline, from squibs) → Say More / Why from pre‑generated cards.
- **P3 — Live depth:** on‑device/hub LLM for arbitrary Say‑More/Why follow‑ups grounded in the bundle.
- **P4 — Map + polish:** map view, re‑entry catch‑up, pre‑rendered audio, the other renderers (Cesium 3D / AR) on the same contract.
