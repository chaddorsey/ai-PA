# 21-14 Validate moved events for all participants

[Back to task list](./tasks.md)

## Description

Currently, the scheduling orchestrator suggests moving events without validating that the new location is conflict-free for all participants of the moved event. This can result in infeasible suggestions that cannot actually be enacted. This task implements validation to ensure all suggested moves are valid (do not result in conflicts for any participants of the moved event) and enforces that only internal-only meetings can be moved.

## Requirements

1. **Store attendee information**: Ensure `attendees` list is stored in `event_metadata` and create `event_participants` mapping to track all participants per event.

2. **Enforce internal-only constraint**: Add hard constraint that only internal-only meetings can be moved (reject external events).

3. **Multi-participant conflict validation**: Validate that moved events don't conflict with any of their participants' calendars (not just the owner).

4. **Targeted calendar fetching**: Proactively fetch calendars for participants of moved events who are not in the original request (the "targeted search" requirement).

5. **Post-solution validation**: Validate all proposals after generation and reject invalid moves from the solution set.

6. **Maintain performance**: Validation should not significantly impact execution time (< 2x overhead).

## Implementation Plan

### Phase 1: Data Structure Updates
- Store `attendees` list in `event_metadata` in `normalizer.py`
- Create `event_participants` mapping: `Dict[Tuple[str, str], List[str]]` to track all participants per event

### Phase 2: Internal-Only Enforcement
- Add hard constraint in `python_solver.py` and `clingo_wrapper.py` to only consider internal-only events for moving

### Phase 3: Multi-Participant Conflict Validation
- Create validation function that checks all participants' calendars for conflicts
- Function assumes all participant calendars are already available (fetched in Phase 5)

### Phase 4: Post-Solution Validation
- Add validation step after building proposals to reject invalid moves

### Phase 5: Targeted Calendar Fetching (Proactive)
- Identify participants from moved events not in original request
- Fetch their calendars via MCP before validation runs
- Update `normalized_data` with new participants' calendar data

**Implementation Order**: Phase 1 → Phase 2 → Phase 5 → Phase 3 → Phase 4
