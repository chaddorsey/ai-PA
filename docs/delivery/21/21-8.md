## Requirements
- Wire DSPy extraction → normalizer → clingo solver → proposal builder
- Integrate explanation generation
- Ensure deterministic, bounded execution
- Handle all error cases gracefully (bad_input, unsat, timeout, etc.)
- Return properly formatted ResponseEnvelope

## Implementation Plan
1. Implement main orchestration flow:
   ```python
   def orchestrate_scheduling(utterance, events_by_participant, context_json=None):
       # 1. Validate inputs
       if not events_by_participant:
           return bad_input_response()
       
       # 2. DSPy extraction
       problem_delta = dspy_extract(utterance, context_json)
       
       # 3. Normalize events to grid
       grid_facts = normalize_events(events_by_participant, context_json)
       
       # 4. Generate ASP facts
       asp_facts = generate_facts(grid_facts, problem_delta)
       
       # 5. Solve with clingo
       result = clingo_solve(asp_facts, timeout=30)
       
       # 6. Handle results
       if result.status == "unsat":
           relaxations = analyze_unsat(result)
           return unsat_response(relaxations)
       
       # 7. Build proposals
       proposals = build_proposals(result.model, grid_facts, context_json)
       
       # 8. Generate explanation
       explanation = generate_explanation(proposals, result.objective_scores)
       
       # 9. Return response
       return ok_response(proposals, explanation, result.debug)
   ```
2. Integrate all components:
   - Import modules from tasks 21-2 through 21-7
   - Wire data flow between components
   - Handle data format conversions
3. Add error handling:
   - Input validation (empty events, malformed context_json)
   - DSPy extraction failures (fallback to basic parsing)
   - clingo timeout (return partial results or unsat)
   - Model extraction failures (graceful degradation)
4. Ensure determinism:
   - Use fixed random seeds for DSPy if needed
   - Sort inputs consistently (participants, events)
   - Use deterministic ASP solving (no random choices)
5. Add bounds checking:
   - Limit horizon size (e.g., max 4 weeks)
   - Limit participant count (e.g., max 10)
   - Limit number of events per participant (e.g., max 100)
   - Enforce timeout on clingo solve
6. Build proposal objects:
   - Convert ASP model to Proposal objects
   - Calculate moved events and objective scores
   - Format times in UTC and participant timezones
7. Generate explanations:
   - Use DSPy or template-based explanation generation
   - Include key decision factors (why this slot was chosen)
   - Mention trade-offs (e.g., "moved standup by 15m to create 2h focus block")

## Verification

- All error cases handled gracefully
- Execution is deterministic (same inputs produce same outputs)
- Bounds are enforced (large inputs rejected or truncated)
