## Requirements
- Compare `projectOperations.list` outputs across `minimal`, `standard`, and `full` detail levels.
- Inspect `listProjects` quick tool responses, including `listByFolder`, `listProjectNames`, and completion-state filtering flags.
- Identify missing fields (timestamps, folder metadata, task summaries, completion status) and note required new structures.
- Record serialization helpers in the plugin that need extension.

## Implementation Plan
- Capture representative tool responses via MCP calls (covering completion-state filters) and store snippets in the task notes.
- Trace server handler code paths to understand trimming logic and where folder data is dropped.
- Review plugin (`omnifocus-mcp.omnijs`) for existing helper utilities like `serializeTimestamped` that can be reused.
- Summarize findings in this task file to guide downstream implementation tasks.

## Verification
- Confirm documented gaps align with observed tool outputs.
- Ensure findings cover both server-side trimming and plugin serialization deficiencies.

## Findings
- `projectOperations.list` ignores incoming filter arguments and always calls `callOmniFocus({ command: "listProjects", args: {} })`, so completion-state filtering is currently impossible from the server.
- The OmniFocus plugin `lib.listProjects` returns only `{ id, name, added, modified }`, leaving `added`/`modified` as `null` when OmniFocus omits timestamps; there is no folder metadata or completion flag.
- Because the bridge payload lacks heavy fields, `filterResponseByDetailLevel` emits identical data for `standard` and `full` detail levels, defeating the user story.
- Quick tool `listProjects` rebuilds summaries but still consumes the same lean payload; it never sets `folderId`/`folderName` because those fields are absent, and its `listByFolder` grouping collapses everything into the root group.
- When `listProjectNames` is false, we still override `taskIds` with a map of `taskItems` (empty) which erases task IDs in the response.
