## Architecture Overview
```
┌──────────────────┐        REST / MCP        ┌────────────────────┐
│   Letta Agents   │ <─────── commands ─────▶ │ Scheduling Service │
└──────────────────┘                         │  (FastAPI + APS)   │
        ▲                                    └─────────┬──────────┘
        │                                                 │
        │ reminders / search results                      │ job execution events
        │                                                 ▼
┌──────────────────┐                               ┌────────────────────┐
│ External Systems │◀── HTTP/Webhook/Script ──────▶│  Action Executors  │
└──────────────────┘                               └────────────────────┘
                                                        │
                                                        ▼
                                               ┌────────────────────┐
                                               │  PostgreSQL w/     │
                                               │  pgvector (jobs,   │
                                               │  executions, logs) │
                                               └────────────────────┘
```
- **Service container**: Python 3.12 image running FastAPI, APScheduler, SQLAlchemy, sentence-transformer embedding pipeline.
- **Persistence**: Single Postgres schema `scheduler` for tables, with pgvector columns enabling semantic search across reminders and action outputs.
- **Embeddings flow**: Textual content (title, body, metadata, execution summaries) sent through local embedding model (e.g., `sentence-transformers/all-MiniLM-L6-v2`); vectors stored in `vector` columns alongside raw text.
- **Execution pipeline**: APScheduler job runner dequeues due jobs, logs execution metadata, triggers HTTP/webhook/script actions, records results, and optionally notifies Letta via callback endpoint.
- **Letta integration**: MCP tool issues REST calls; Letta can also subscribe/poll for execution history.
- **Scalability**: Designed for <100 daily jobs; single-instance scheduler sufficient but schema allows future horizontal scale via distributed lock table.

## Database Schema
Schema name: `scheduler`

| Table | Purpose | Key Columns |
|-------|---------|-------------|
| `jobs` | Authoritative job definition. | `job_id UUID PRIMARY KEY`, `title TEXT`, `description TEXT`, `status TEXT`, `schedule_type TEXT` (`cron`, `interval`, `one_off`), `schedule_expression JSONB`, `next_run_at TIMESTAMPTZ`, `created_at`, `created_by`, `updated_at`, `vector_embedding vector(384)` |
| `job_metadata` | Arbitrary metadata / key-value context. | `job_id` FK → `jobs`, `meta_key TEXT`, `meta_value JSONB`, `embedding vector(384)` |
| `actions` | Configured actions associated with a job. | `action_id UUID PK`, `job_id` FK, `action_type TEXT` (`http`, `webhook`, `script`), `config JSONB`, `allow_list_tag TEXT`, `created_at`, `updated_at` |
| `executions` | Individual job execution records. | `execution_id UUID PK`, `job_id` FK, `scheduled_at`, `started_at`, `completed_at`, `status TEXT`, `retry_count INT`, `log_summary TEXT`, `result_reference TEXT`, `vector_embedding vector(384)` |
| `execution_outputs` | Structured output blobs for actions. | `execution_id` FK, `action_id` FK, `output_type TEXT`, `output_data JSONB`, `artifact_uri TEXT`, `created_at` |
| `callbacks` | Optional Letta callback targets. | `callback_id UUID PK`, `job_id` FK, `callback_url TEXT`, `secret_token TEXT`, `enabled BOOLEAN`, `created_at` |
| `audit_log` | Track create/update/delete operations. | `audit_id BIGSERIAL PK`, `entity_type TEXT`, `entity_id UUID`, `action TEXT`, `actor TEXT`, `timestamp`, `details JSONB` |
| `distributed_lock` | Ensures single runner processes jobs. | `lock_name TEXT PK`, `owner_id TEXT`, `expires_at TIMESTAMPTZ` |

Entity relationships:
- One `job` → many `actions`, `job_metadata` entries, and `executions`.
- Each `execution` may have multiple `execution_outputs` (one per action invocation).
- `callbacks` optionally associated one-to-one or one-to-many with `job` (allowing multiple listeners per job).
- `audit_log` captures changes across all entity types using generic references.
- `distributed_lock` enforces single scheduler ownership; `owner_id` is instance UUID persisted in memory.

Indexes & constraints:
- `jobs_next_run_idx` on `(next_run_at)` for ready queue queries.
- `jobs_status_idx` on `(status)` for filtering by state.
- GIN index on `job_metadata.meta_value` for JSON queries.
- `executions_job_scheduled_idx` on `(job_id, scheduled_at DESC)`.
- pgvector indexes (HNSW or IVFFlat) on `jobs.vector_embedding`, `job_metadata.embedding`, `executions.vector_embedding` for semantic similarity.

Migration strategy:
- Alembic revision `001_create_scheduler_schema` to create schema, extensions (`CREATE EXTENSION IF NOT EXISTS vector;`), tables, indexes.
- `002_add_actions_and_callbacks` reserved for future expansions.

Example DDL excerpt for `001_create_scheduler_schema`:
```
CREATE SCHEMA IF NOT EXISTS scheduler;
SET search_path TO scheduler;

CREATE TABLE jobs (
  job_id UUID PRIMARY KEY,
  title TEXT NOT NULL,
  description TEXT,
  status TEXT NOT NULL DEFAULT 'scheduled',
  schedule_type TEXT NOT NULL,
  schedule_expression JSONB NOT NULL,
  next_run_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  created_by TEXT NOT NULL,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  vector_embedding vector(384)
);

CREATE INDEX jobs_next_run_idx ON jobs (next_run_at);
CREATE INDEX jobs_status_idx ON jobs (status);
CREATE INDEX jobs_embedding_idx ON jobs USING ivfflat (vector_embedding vector_cosine_ops)
  WITH (lists = 100);
```

## API Surface (REST)
- `POST /v1/jobs` – Create job; validates schedule expression, action configs, metadata, optional immediate execution flag.
- `GET /v1/jobs` – List/filter jobs by status, tag, timeframe.
- `GET /v1/jobs/{job_id}` – Retrieve full job details including actions and next run.
- `PATCH /v1/jobs/{job_id}` – Update schedule, metadata, actions; supports partial updates.
- `DELETE /v1/jobs/{job_id}` – Soft-delete (status → `cancelled`) with audit entry.
- `POST /v1/jobs/{job_id}/trigger` – Trigger immediate execution; records manual invocation source.
- `POST /v1/jobs/{job_id}/pause` / `/resume` – Toggle scheduling.
- `GET /v1/jobs/{job_id}/executions` – Paginated history with filters.
- `GET /v1/executions/{execution_id}` – Detailed execution log, outputs, status, embeddings.
- `POST /v1/search` – Combined keyword + vector similarity search across jobs/executions/metadata; accepts text query and filters.
- `POST /v1/actions/test` – Dry-run validation for action configuration (no scheduling).
- `GET /v1/healthz`, `/readyz`, `/metrics` – Health and telemetry endpoints.
- `POST /v1/callbacks` – Register callback target tied to job; optional HMAC secret.
- `DELETE /v1/callbacks/{callback_id}` – Remove callback.

API conventions:
- Request/response bodies defined via Pydantic models with explicit field descriptions.
- All timestamps ISO8601 with timezone.
- Errors follow JSON API pattern: `{ "error": { "code": "validation_error", "message": "...", "hints": ["..."] } }`.
- Include `x-job-version` header on job endpoints to support optimistic concurrency.
- Use pagination via `limit`/`offset` query params on list endpoints.

## MCP Command Contract
- `schedule_reminder`
  - Inputs: `title`, `message`, `scheduled_for`, optional `repeat` descriptor, `tags`, `actions`, `callback`.
  - Outputs: job summary (ID, next run, actions).
  - Validation hints when schedule malformed or missing.
- `schedule_series`
  - Inputs: recurrence rule (`RRULE`, `interval`, or `cron`), time range, template message, optional metadata.
  - Outputs: parent job ID and generated occurrences.
- `list_jobs`
  - Inputs: optional filters (status, date range, tag, text query).
  - Outputs: array of job summaries.
- `search_archive`
  - Inputs: `query_text`, optional filters; triggers vector search.
  - Outputs: ranked matches with `similarity_score`, `snippet`, `execution_metadata`.
- `update_job`
  - Inputs: job ID + partial updates.
  - Outputs: updated job summary.
- `cancel_job`
  - Inputs: job ID, optional reason.
  - Outputs: confirmation; ensures future runs halted.
- `trigger_now`
  - Inputs: job ID, optional override metadata.
  - Outputs: execution record reference.
- `register_action`
  - Inputs: job ID or standalone action definition; returns action ID for linkage.
- Tool errors include suggestions (e.g., “Use ISO format `YYYY-MM-DDTHH:MM:SSZ` for scheduled times”).

## Docker Compose Integration
- Service name: `scheduler-service`.
- Dockerfile: based on `python:3.12-slim`; installs Poetry/pip deps including `fastapi`, `uvicorn`, `apscheduler`, `sqlalchemy`, `asyncpg`, `pgvector`, `sentence-transformers`, `httpx`, `structlog`, `alembic`.
- Compose snippet example:
  ```yaml
  scheduler-service:
    build:
      context: ./scheduler-service
      dockerfile: Dockerfile
    depends_on:
      supabase-db:
        condition: service_healthy
    environment:
      SCHEDULER_DB_URL: postgresql+asyncpg://scheduler:${SCHEDULER_DB_PASSWORD}@supabase-db:5432/scheduler
      EMBEDDING_MODEL_NAME: sentence-transformers/all-MiniLM-L6-v2
      API_KEY: ${SCHEDULER_API_KEY:-}
      ALLOWLIST_SCRIPT_DIR: /app/scripts
      LETTA_CALLBACK_URL: http://letta:8283/v1/tools/scheduler
      LOG_LEVEL: INFO
      METRICS_ENABLED: "true"
    volumes:
      - ./scheduler-service/scripts:/app/scripts:ro
    networks: [pa-internal]
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8087/healthz"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 30s
    ports:
      - "8087:8087"  # optional, only if external access needed
    command: ["uvicorn", "scheduler.main:app", "--host", "0.0.0.0", "--port", "8087"]
  ```
- Create dedicated Postgres role `scheduler` with schema `scheduler`; migrations run via `docker compose run scheduler-service alembic upgrade head` or init container.
- Ensure `.env` includes credentials: `SCHEDULER_DB_PASSWORD`, `SCHEDULER_API_KEY` (optional), `EMBEDDING_MODEL_NAME`.
- Join existing `pa-internal` network; no additional network required initially.

## Security & Observability Considerations
- **Network**: Keep service internal-only; rely on Cloudflare tunnel or Letta MCP for external interactions if ever needed.
- **Authentication**: Optional API key header `X-API-Key` for REST calls; MCP tool stores secret in config. Initial deployment can rely on network isolation if user prefers minimal auth.
- **Secrets management**: Use Compose `.env` or Docker secrets for DB password/API key. Avoid logging sensitive payloads.
- **Logging**: Structured JSON logs using `structlog` with fields `job_id`, `execution_id`, `action_type`, `status`.
- **Metrics**: Expose Prometheus endpoint with scheduler stats (jobs scheduled, executions success/fail, queue latency).
- **Tracing**: Provide OpenTelemetry hooks for future integration.
- **Backups**: Scheduler schema included in Postgres backups; embeddings stored inline so no separate store needed.
- **Auditability**: Audit log table supports downstream analytics/RAG ingestion; ensure retention policy aligns with storage constraints.
